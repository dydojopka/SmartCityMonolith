## Как работать в своей ветке

Команды выполняешь ты вручную из корня **нового** репозитория. Если уже есть локальная копия, второй раз клонировать её не нужно. Перед переключением ветки `git status` должен быть понятным: не сбрасывай и не прячь неизвестные изменения автоматически.

```bash
git status
git remote -v
git fetch origin
git switch main
git pull --ff-only origin main
git switch -c work/zheNYA
```

`git switch -c` нужен только один раз; впоследствии `git switch work/zheNYA`. Если `pull --ff-only` отказал из-за локальных коммитов, сначала выяснить расхождение, без `reset --hard` и force push.

Перед коммитом посмотреть фактические изменения и тесты. Добавлять только свои конкретные файлы, например:

```bash
git diff
git add .gitignore docs/API_CONTRACT.md
git diff --cached
git commit -m "Зафиксировать контракт модульного монолита"
git push -u origin work/zheNYA
```

Это пример для договорённости/контракта, не команда добавить все файлы пункта 1: остальные файлы добавляются явно после проверки. `.local` не добавлять, в том числе через `git add -f`. Коммиты выполняет сам участник.

На GitHub: **Pull requests → New pull request**, base `main`, compare `work/zheNYA`. Проверить **Files changed**, описать результат, выполненные проверки и ограничения; назначить Данила reviewer. Незавершённое - **Draft**. Не включать приватные заметки в описание PR.

Для обновления своей ветки перед следующим этапом:

```bash
git fetch origin
git switch work/zheNYA
git merge origin/main
git push
```

Конфликт решать по смыслу, не выбирать массово «всё наше/всё их». Сначала проверить результат, затем завершить merge обычным коммитом. Для нескольких PR из одной ветки использовать **Create a merge commit**, не удалять ветку до завершения всех этапов. После merge повторять синхронизацию с `main`, не переигрывать историю опубликованной ветки.
