# Модульный монолит: объединение двух микросервисов на практике

## Цель работы

Сравнить на практике две архитектуры: объединить два микросервиса проекта «Умный город» в одно приложение — **модульный монолит**, заменить сетевое взаимодействие внутренними вызовами и сравнить обе версии по измеримым показателям. Цель — понять, что даёт и чего стоит каждый из подходов.

## Исходные данные

Экосистема микросервисов «Умный город», разработанная в предыдущем проекте:

- Identity & Auth Service
- Transport Service
- Utility Service
- Environment Service
- Billing & Payment Service
- Notiﬁcation Service

Каждый сервис имеет собственную базу данных и взаимодействует с другими сервисами только через HTTP API.

Работа выполняется на тех же языке программирования и фреймворке, на которых разрабатывались микросервисы Вашей команды.

## Что такое модульный монолит

**Модульный монолит** — это одно приложение (один процесс, одна база данных, одно развёртывание), код которого разделён на модули с

чёткими границами. От обычного монолита он отличается тем, что модули остаются почти такими же независимыми, как микросервисы, но общаются друг с другом без сети.

```
Микросервисы                                    Модульный монолит

┌──────────────┐   HTTP    ┌──────────────┐     ┌───────────────── одно приложение ─────────────────┐
│   Billing    │ ────────► │ Notification │     │ ┌────────────┐  вызов метода  ┌────────────────┐  │
│   Service    │           │   Service    │     │ │  billing   │ ─────────────► │  notification  │  │
└──────┬───────┘           └──────┬───────┘     │ │   модуль   │   или событие  │     модуль     │  │
       │                          │             │ └─────┬──────┘                └───────┬────────┘  │
   ┌───▼───┐                  ┌───▼───┐         └───────┼───────────────────────────────┼───────────┘
   │ БД 1  │                  │ БД 2  │                 └──────────► одна БД ◄───────────┘
   └───────┘                  └───────┘                       (схема billing, схема notification)
```

Три правила модульного монолита:

| Правило             | Что это значит |
|---------------------|----------------|
| **Публичный интерфейс** |Каждый модуль предоставляет другим модулям один класс-«фасад» (например, `BillingApi`) или набор событий. Всё остальное — внутренние детали, которые другим модулям использовать запрещено.|
| **Свои данные**         | Каждый модуль работает только со своими таблицами. Запросы к таблицам другого модуля (в том числе `JOIN`) запрещены — нужные данные получают через публичный интерфейс. |
| **Нет циклов**          | Если модуль A обращается к модулю B, то B не обращается к A напрямую. Обратная связь — через события. |

Соблюдение этих правил позволяет в будущем снова выделить модуль в отдельный микросервис с минимальными изменениями.

## Задание

### 1. Карта взаимодействия сервисов
Изучите свою реализацию «Умного города» и составьте схему: какие сервисы обращаются к каким и через какие endpoints. Например:

Billing → Notiﬁcation: `POST /notifications`.

Для каждого межсервисного вызова укажите, что произойдёт с исходной операцией, если вызываемый сервис недоступен.

### 2. Выбор сервисов и сценария

Выберите **два** сервиса, между которыми есть хотя бы один сценарий взаимодействия (один сервис вызывает другой). Примеры пар:

| Пара сервисов                    | Пример сценария |
|----------------------------------|-----------------|
| Billing & Payment + Notification | `POST /payments/webhook/success` — платёж подтверждён, Billing вызывает `POST /notifications`, чтобы уведомить пользователя |
| Utility + Notification           | `PUT /issues/{id}` — статус заявки ЖКХ изменён, автор заявки получает уведомление |
| Environment + Notification       | `POST /sensors/data` — значение датчика превысило допустимое, рассылается оповещение |
| Transport + Billing & Payment    | `POST /parking/{id}/reserve` — бронирование парковки создаёт счёт на оплату |
| Identity & Auth + любой сервис   | при создании заявки или платежа сервис проверяет пользователя через `GET /users/{id}` |

Можно выбрать другую пару. Если в Вашей реализации сервисы ещё не взаимодействуют, реализуйте в микросервисной версии простейший сценарий из таблицы.

Опишите выбранный сценарий по шагам: какой запрос приходит от клиента, какой сервис кого вызывает, что сохраняется в базах данных. Объясните, почему выбрана именно эта пара (2–3 предложения).

> При сдаче задания потребуется приложить отчёт.

### 3. Сборка модульного монолита

1. Создайте новое приложение  `smart-city-monolith`, в котором код двух сервисов оформлен как модули в отдельных каталогах, например `modules/billing` и `modules/notification`.
2. Для модуля, к которому обращаются, создайте **публичный интерфейс** — один класс или файл, через который другие модули его используют.
3. Замените HTTP-вызов между сервисами одним из способов:
   - **вариант А — прямой вызов:** модуль billing вызывает метод публичного интерфейса модуля notiﬁcation;
   - **вариант Б — внутреннее событие:** модуль billing публикует событие «Платёж проведён», а модуль notiﬁcation его обрабатывает. Billing ничего не знает о том, кто подписан на событие.
4. Сохраните **внешний REST API** без изменений: адреса и формат запросов и ответов должны остаться прежними, чтобы клиентская часть проекта продолжила работать без доработок. Внутренний endpoint, который был нужен только для вызова из другого сервиса (например,  `POST /notifications`), в монолите можно убрать — объясните в отчёте, почему.

В отчёте объясните, почему выбран вариант А или Б.

> **Примечание:** средства для внутренних событий есть в большинстве платформ: в Node.js — встроенный `EventEmitter` (в NestJS — пакет  @nestjs/event-emitter ), в Spring — ApplicationEventPublisher, в .NET — уведомления библиотеки MediatR. Для этой работы достаточно простейшего варианта.

### 4. Единая база данных

1. Используйте **одну** базу данных. Таблицы каждого модуля разместите отдельно:
    - PostgreSQL — в отдельных схемах (`billing`, `notification`);
    - MySQL — с префиксом в имени таблицы (`billing_payment`, `notification_message`).
2. Модули не обращаются к таблицам друг друга.
3. Подготовьте SQL-скрипт (или миграцию), который создаёт структуру и заполняет тестовыми данными.

В отчёте ответьте на вопрос: нужно ли создавать **внешний ключ** между таблицами разных модулей (например, `notification_message.payment_id → billing_payment.id`)? Что даёт такой ключ и чем он мешает, если модуль в будущем снова станет отдельным сервисом?

5. Сравнение версий

Запустите обе версии **на одном и том же компьютере** и измерьте для выбранного сценария:

| Показатель                                    | Микросервисы | Модульный монолит |
|-----------------------------------------------|--------------|-------------------|
| Среднее время ответа, мс                      |              |                   |
| Запросов в секунду                            |              |                   |
| Используемая память, МБ                       |              |                   |
| Количество запущенных процессов (контейнеров) |  |  |
| Количество команд для запуска системы         |  |  |

Как измерять:

- **время ответа и запросы в секунду** — отправьте не менее 200 запросов, например программой Apache Bench (входит в Xampp: `xampp\apache\bin\ab.exe`) или `npx autocannon`:

```shell
# GET-запрос: 200 запросов, по 10 одновременно
ab -n 200 -c 10 http://localhost:3000/api/...

# POST-запрос с телом из файла body.json
ab -n 200 -c 10 -p body.json -T application/json http://localhost:3000/api/...
```

- **память** — в Диспетчере задач (вкладка **Подробности**) сложите память всех процессов системы: серверов приложений и СУБД; если сервисы запускаются в Docker — используйте команду  `docker stats`.

Повторите каждый замер 3 раза и запишите среднее значение.

### 6. Эксперимент с отказом

Временно сделайте так, чтобы модуль (сервис) уведомлений выбрасывал ошибку при обработке. Проверьте в **обеих** версиях и опишите:

- завершается ли основная операция (например, платёж) успешно, если уведомление не удалось отправить;
- что видит клиент в ответе;
- как бы Вы изменили код, чтобы ошибка второстепенного модуля не ломала основной сценарий.
