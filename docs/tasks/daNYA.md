# Шилов Данил — daNYA

Твоя ветка: `work/daNYA`. Объём — около 12 единиц: Utility, его надёжность и измерения. **До начала работы прочитай [общий план](../PLAN.md), включая раздел 4 о замерах и отказе.** После Z1 Евгения также прочитай [API-контракт](../API_CONTRACT.md). Одного этого чек-листа недостаточно: общий контракт и порядок интеграции определены планом. README не менять.

Пути `app/`, `tests/`, `benchmarks/` относятся к `smart-city-monolith/`, а `docs/` — к корню репозитория. Пустые файлы в каркасе не являются готовой реализацией или выполненными тестами.

## Когда начинать и где работать

Дождись первого PR Евгения с каркасом и `docs/API_CONTRACT.md`. До этого можно изучать исходный `smart-city/services/utility-service/` и готовить перечень тестов. Код исходного SmartCity не изменяй.

Твои основные файлы:

- `smart-city-monolith/app/modules/utility/` — router, модели, схемы, seed, адаптер уведомлений;
- `smart-city-monolith/tests/test_utility.py`;
- `smart-city-monolith/benchmarks/run.py`, `benchmarks/results/`.

Общие `main.py`, `database.py`, `auth.py`, `dependencies.py`, `conftest.py`, Compose и requirements принадлежат Евгению. Если нужен общий пакет/fixture/изменение сигнатуры — согласуй до правки, не делай альтернативный engine или вторую JWT-проверку. Notification внутри не изменяй.

## D1. Перенос Utility — 4 единицы

- [ ] Перенести `Issue`, `IssueCreate`, `IssueResponse`, `IssueStatusUpdate` из исходного Utility, поправить импорты на новую структуру. Таблица только `utility.issues`, `Base` и UTC — из общего `app.database`.
- [ ] Сохранить все поля, длины/валидацию, статусы `NEW/IN_PROGRESS/RESOLVED/REJECTED`, индексы, ограничение уникальности `(user_id, request_key)` и временные метки UTC. Не добавлять FK на Identity/Notification.
- [ ] Вместо отдельного `FastAPI` использовать `APIRouter`; перенести `POST /issues`, `GET /issues`, `PUT /issues/{issue_id}`. Не добавлять префикс `/utility` или `/api`, которого раньше не было.
- [ ] `POST`: оставить очистку строк/категории, `201`, безопасный replay `200`, конфликт содержимого `409`, восстановление после проигранной гонки уникальности через rollback и повторное чтение.
- [ ] `GET`: USER видит только свои записи, OPERATOR/ADMIN — все, прежний порядок по `created_at` убыванию.
- [ ] `PUT`: только OPERATOR/ADMIN, `404` для отсутствующей заявки; сохранить атомарный `UPDATE ... WHERE status != new_status`, commit и refresh. Уведомление вызывается только при реально изменённой строке.
- [ ] В `utility/notifications.py` заменить HTTP на `NotificationApi.send(...)`. Получать экземпляр через общий `get_notification_api()`/Depends, а не создавать второй engine. Разрешён импорт только `app.modules.notification.api`, не моделей или таблицы соседа.
- [ ] Оставить исходные PUSH, recipient/user_id, subject и message из PLAN. Вызов после commit заявки; фасад использует свою сессию.
- [ ] Перехватывать `Exception` только вокруг вызова уведомления, логировать `issue_id` и ошибку без секретов, не возвращать клиенту `500` из-за побочного эффекта. Не оборачивать весь endpoint в подавляющий ошибки try/except.
- [ ] Перенести идемпотентный seed заявки `90000000-0000-0000-0000-000000000001` с автором `00000000-0000-0000-0000-000000000001`. Не запускать seed при импорте и не удалять пользовательские данные.

## D2. Проверки Utility и устойчивости — 3 единицы

Добавляй в `tests/test_utility.py`, используя выделенную тестовую PostgreSQL-БД из каркаса. Старые SQLite fixtures нельзя просто скопировать: PostgreSQL-схемы и реальная конкуренция требуют настоящей новой БД. Из исходных `test_api.py`, `test_regressions.py`, `test_adversarial.py` перенеси подходящие проверки, а не импортируй старый пакет `app`.

- [ ] Создание/чтение, нормализация и UTC `Z`; неверные поля → `422`.
- [ ] Нет/невалидный/просроченный JWT → `401`; USER не обновляет статус → `403`; корректные роли OPERATOR/ADMIN работают.
- [ ] Чужие заявки скрыты от USER, видны оператору; неизвестная заявка → `404`.
- [ ] Повтор одинакового POST с ключом даёт тот же ID/`200`; другой payload с тем же ключом → `409`; без ключа создаются разные заявки.
- [ ] Два параллельных POST с одним ключом создают ровно одну запись, без `500`. Применить также конфликтующее содержимое; не ослаблять уникальный индекс ради теста.
- [ ] Смена статуса вызывает фасад с точным payload ровно один раз; тот же статус повторно — ноль новых вызовов.
- [ ] Два параллельных PUT с одинаковым целевым статусом создают только одно уведомление. Не тестировать лишь последовательный replay вместо гонки.
- [ ] Исключение фасада не меняет `200`/JSON успешной заявки; новое чтение из БД подтверждает сохранённый статус. Проверяется лог ошибки.
- [ ] Согласовать с Евгением сквозной тест с настоящим Notification, чтобы unit-тесты с подменой фасада не были единственным доказательством интеграции.

**Первый PR:** «Перенос Utility и тесты». Можно открыть Draft до готовности Notification, но не объявлять сквозную проверку пройденной до интеграции.

## D3. Один инструмент для двух версий — 3 единицы

После интеграции и Z2 Евгения подготовь `benchmarks/run.py` на имеющихся Python/HTTPX/PyJWT и стандартной библиотеке. Без нового нагрузочного фреймворка. Сначала зафиксируй его реальный CLI и передай короткие команды Ивану; ниже — требования к поведению, не обещание уже существующей программы.

- [ ] Принимать URL выбранной версии, тестовый JWT-secret/настройки безопасным способом, выходной каталог. Секреты не хранить в аргументах результатов, JSON/CSV или логах.
- [ ] Создавать валидные тестовые USER и OPERATOR JWT с `sub/role/exp`; не отключать авторизацию сервера. Использовать демо-данные и достаточно долгий срок JWT для одного эксперимента.
- [ ] Перед каждым прогоном через API создать N+20 отдельных заявок: 20 прогревочных и N измеряемых, все `NEW`, N ≥ 200. Первоначально N=200. Сохранить соответствие ID заявок прогону. Не использовать один ID для 200 одинаковых PUT и не повторять один `X-Idempotency-Key` для разных заявок.
- [ ] 20 PUT прогрева вне времени, затем N PUT `NEW → IN_PROGRESS`, одновременно не более 10 запросов. Повторить 3 раза для каждой версии на одной машине с одинаковым N. Если нагрузка слишком коротка для нескольких снимков памяти, выбрать общее большее N и повторить обе серии, не добавлять искусственных задержек.
- [ ] Для latency использовать `perf_counter()` непосредственно вокруг каждого HTTP-запроса, не включая очередь подготовки задач. Для RPS измерять wall time всего пакета; одинаковые настройки клиента/keep-alive у обеих версий.
- [ ] Сохранять все длительности, коды ответа, количество ошибок и метаданные запуска без токенов. При не-`200`, неправильном JSON или неподтверждённом побочном эффекте помечать прогон невалидным, не скрывать ошибки средним числом.
- [ ] Вместе с Евгением проверить N сохранённых новых статусов и N SENT именно измеряемых заявок: baseline читает свою SQLite, mono свою PostgreSQL. Скрипт проверки/измерения может читать обе таблицы как внешний диагностический инструмент — бизнес-модулям это по-прежнему запрещено.
- [ ] Во время каждого пакета собрать снимки памяти всех контейнеров стенда, включая PostgreSQL; сохранить сумму, интервалы, единицы, правило усреднения. Проверить, что замер успел снять память во время нагрузки, а не только до/после.
- [ ] Сохранить по три результата, затем среднее latency/RPS/памяти. Зафиксировать реальные контейнеры и команды запуска, ОС/железо/версии/SHA, не подгонять значения под ожидаемую экономию.
- [ ] Явно написать ограничение: исходная micro-версия на SQLite, mono на PostgreSQL; это сравнение реализаций, не чистый эффект замены HTTP вызовом метода.

## D4. Отказ и передача доказательств — 2 единицы

- [ ] На каждой версии включить согласованный `NOTIFICATION_FAIL_SEND`, выполнить смену статуса **новой** заявки и сохранить очищенные HTTP/JSON, лог и состояния двух модулей.
- [ ] Проверить: клиент Utility получает `200`, заявка в новом статусе, уведомление `PENDING`, `sent_at=NULL`; micro-Notification действительно ответил `500` из-за ошибки обработки. Если наблюдение иное — оформить дефект, не подставлять ожидаемый результат в отчёт.
- [ ] Выключить режим, на другой новой заявке показать `SENT`. Не называть это повторной доставкой прежнего PENDING: retry в реализации нет.
- [ ] Передать Ивану `benchmarks/results/` с таблицей «3 прогона + среднее» и фактами отказа; проверить его итоговые числа в PDF. Условия измерений должны быть воспроизводимы без доступа к твоей личной папке.
- [ ] Второй PR: «Измерения и эксперимент с отказом». Если измеряемый код изменился после результатов, повторить затронутые прогоны.

## Ветка, коммиты и PR

Если нет локальной копии, сначала один раз:

```bash
git clone https://github.com/dydojopka/SmartCityMonolith.git
cd SmartCityMonolith
```

Иначе открой существующий **новый** репозиторий, не соседний SmartCity. После готовности каркаса:

```bash
git status
git remote -v
git fetch origin
git switch main
git pull --ff-only origin main
git switch -c work/daNYA
```

Если Git сообщает о неизвестных изменениях или расходящейся истории — остановись и обсуди с Евгением; не используй `reset --hard`/force push. Ветка создаётся один раз, потом переключается через `git switch work/daNYA`.

Из `smart-city-monolith/` запускай подготовленные в Z1 команды тестов, как минимум свои `python -m pytest -q tests/test_utility.py` с безопасной тестовой БД; интеграционные — после подключения фасада. Из корня Git:

```bash
git diff
git add smart-city-monolith/app/modules/utility smart-city-monolith/tests/test_utility.py
git diff --cached
git commit -m "Перенести модуль заявок с внутренним вызовом уведомлений"
git push -u origin work/daNYA
```

Пример относится к первому PR; инструмент и результаты второго добавляй отдельно после проверки отсутствия секретов. Коммиты выполняешь сам, `.local` не добавляешь даже с `-f`.

GitHub: **Pull requests → New pull request**, base `main`, compare `work/daNYA`. Кратко указать результат, тесты/прогоны и ограничения; reviewer — Евгений. Проверить **Files changed**: только согласованная область, без README. Незаконченное — Draft. Поправки после ревью коммитятся и отправляются в ту же ветку, PR обновится сам.

Перед новым этапом и после merge других участников:

```bash
git fetch origin
git switch work/daNYA
git merge origin/main
git push
```

Конфликты в общих файлах согласуй с владельцем, проверь код после разрешения. Для нескольких PR этой ветки договорённость — **Create a merge commit**, без squash/force push; ветку не удалять до окончания измерений. Новый PR для второго этапа открывается после слияния первого и синхронизации с `main`.
