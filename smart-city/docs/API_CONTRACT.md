# API-контракт

## Общие правила

- JSON, идентификаторы UUID, дата и время в UTC (`2026-10-06T12:00:00Z`).
- Авторизация: `Authorization: Bearer <JWT>`. Claims: `sub`, `role`, `exp`;
  роли: `USER`, `OPERATOR`, `ADMIN`.
- Ошибки: `{"detail": "Описание"}`; при валидации `detail` может быть массивом.
- Основные коды: `200` - успех, `201` - создание, `400` - недопустимая операция,
  `401` - неверная авторизация, `403` - нет прав, `404` - не найдено,
  `409` - конфликт, `422` - неверные данные, `502` - ошибка демо-подтверждения.
- У каждого сервиса есть `GET /health`, Swagger `/docs` и `/openapi.json`.
  Полные схемы ответов доступны в Swagger.

## Identity - 8001

| Метод и путь | Доступ | Результат |
|---|---|---|
| `POST /auth/register` | Публичный | Профиль нового USER, `201`; повторный email - `409` |
| `POST /auth/login` | Публичный | `access_token`, `token_type`; неверные данные - `401` |
| `GET /users/me` | JWT | Профиль текущего пользователя |
| `GET /users/{id}` | Публичный | Публичный профиль; неизвестный ID - `404` |
| `GET /users` | JWT | Массив публичных профилей |

Регистрация:

```json
{"email":"user@example.com","password":"password123","first_name":"Иван","last_name":"Иванов"}
```

Вход: `{"email":"user@example.com","password":"password123"}`.
Публичный профиль: `id`, `first_name`, `last_name`, `role`.
Собственный профиль также содержит `email`, `is_active`, `created_at`.
Пароль и его хеш не возвращаются.

## Transport - 8002

| Метод и путь | Доступ | Результат |
|---|---|---|
| `GET /vehicles` | Публичный | Транспорт: `id`, `type`, `route_number`, координаты, `status`, `updated_at` |
| `GET /parking` | Публичный | Парковки: `id`, `name`, `address`, координаты, `total_spaces`, `available_spaces` |
| `POST /parking/{id}/reserve` | JWT | Бронь: `id`, `parking_id`, `user_id`, `status`, `created_at`; `201` |

Бронирование не требует тела. Место списывается атомарно;
нет парковки - `404`, нет мест - `409`.
Необязательный `X-Idempotency-Key` (1–128 символов): повтор тем же пользователем
для той же парковки возвращает прежнюю бронь с `200`, не списывая ещё одно место.
Другой parking_id с прежним ключом - `409`.

## Utility - 8003

| Метод и путь | Доступ | Результат |
|---|---|---|
| `POST /issues` | JWT | Новая заявка, `201` |
| `GET /issues` | JWT | Свои заявки для USER, все для OPERATOR/ADMIN |
| `PUT /issues/{id}` | OPERATOR/ADMIN | Обновлённая заявка |

Создание:

```json
{"title":"Не работает фонарь","description":"Не включается вечером","category":"LIGHTING","address":"Невский проспект, 10"}
```

Ответ содержит поля запроса, `id`, `user_id`, `status`, `created_at`, `updated_at`.
Начальный статус - `NEW`. Изменение: `{"status":"IN_PROGRESS"}`.
Допустимы `NEW`, `IN_PROGRESS`, `RESOLVED`, `REJECTED`.

Необязательный `X-Idempotency-Key` (1–128 символов): повтор с теми же
нормализованными полями возвращает прежнюю заявку с `200`; изменённые данные
с прежним ключом - `409`.

## Environment - 8004

| Метод и путь | Доступ | Результат |
|---|---|---|
| `GET /sensors` | Публичный | Датчики: `id`, `name`, `type`, `unit`, координаты, `status`, `last_seen_at` |
| `GET /sensors/{id}/data` | Публичный | Массив показаний: `id`, `sensor_id`, `value`, `measured_at`, `received_at` |
| `POST /sensors/data` | `X-Sensor-Key` | Сохранённое показание, `201` |

Приём показания:

```json
{"sensor_id":"40000000-0000-0000-0000-000000000001","value":18.7,"measured_at":"2026-10-06T12:00:00Z"}
```

Для истории доступен `?limit=100` (1–1000, по умолчанию 100).
Неверный ключ - `401`, неизвестный датчик - `404`, неактивный - `400`.
Время измерения обязано иметь часовой пояс; ключ датчика и его хеш не возвращаются.

## Billing - 8005

| Метод и путь | Доступ | Результат |
|---|---|---|
| `GET /accounts/{userId}/invoices` | Владелец/ADMIN | Массив счетов |
| `POST /payments` | Владелец счёта | Платёж CREATED, `201`; повтор ключа - `200` |
| `POST /payments/webhook/success` | `X-Service-Token` | Платёж SUCCEEDED, счёт PAID |
| `POST /payments/{payment_id}/demo-success` | Владелец платежа | Серверное демо-подтверждение, `200` |

Счёт: `id`, `user_id`, `description`, `amount_cents`, `status`, `due_date`,
`paid_at`, `created_at`, `updated_at`. Статусы: `PENDING`, `PAID`, `CANCELLED`.
API хранит суммы в целых копейках; сайт показывает рубли с двумя знаками после запятой.

Создание платежа:

```json
{"invoice_id":"50000000-0000-0000-0000-000000000001","idempotency_key":"payment-001"}
```

Сумма берётся из счёта. Ответ: `id`, `invoice_id`, `user_id`, `amount_cents`,
`status`, `idempotency_key`, `external_event_id`, `created_at`, `updated_at`.
Статусы платежа: `CREATED`, `SUCCEEDED`, `FAILED`. Создание само по себе не оплачивает счёт.

Webhook:

```json
{"external_event_id":"provider-event-001","payment_id":"70000000-0000-0000-0000-000000000001"}
```

Успешный webhook в одной транзакции меняет платёж/счёт и заполняет `paid_at`.
Повтор события не создаёт вторую оплату или уведомление.
Один счёт допускает только один активный/успешный платёж; после FAILED можно
создать новую попытку с новым ключом. Ключ/событие нельзя использовать для другого объекта.

Демо-подтверждение не требует тела и доступно при `DEMO_PAYMENTS_ENABLED=true`.
Сервер вызывает webhook по HTTP со служебным токеном и стабильным событием
`demo-payment-<payment_id>`. Повтор безопасен; при `502` повторяют операцию с тем же
ключом. Выключенный демо-режим - `404`, FAILED/отменённый счёт - `409`.
Чужая оплата запрещена даже ADMIN. Реальные деньги не списываются,
`SERVICE_TOKEN` не передаётся браузеру.

## Notification - 8006

`POST /notifications` - внутренний endpoint с `X-Service-Token`, ответ `201`.

```json
{"user_id":"00000000-0000-0000-0000-000000000001","channel":"PUSH","recipient":"00000000-0000-0000-0000-000000000001","subject":"Статус изменён","message":"Ваша заявка принята в работу"}
```

Каналы: `EMAIL`, `SMS`, `PUSH`. Ответ содержит поля уведомления, `id`, `status`,
`created_at`, `sent_at`. Отправка имитируется в логе со статусом `SENT`;
неверный служебный токен - `401`.
