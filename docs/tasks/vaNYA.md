## Что именно нужно сделать

Команда объединяет **Utility (заявки ЖКХ) + Notification (уведомления)** на Python 3.12 / FastAPI / SQLAlchemy. Utility после изменения статуса уже сохраняет заявку и только потом вызывает уведомление. Твоя часть - сделать Notification обычным Python-модулем внутри приложения, а не вторым сервером.

Только твои рабочие каталоги:

```text

```

Внутри модуля будут `__init__.py`, `api.py`, `router.py`, `models.py`, `schemas.py`, `seed.py` при необходимости. Общие `database.py`, `main.py`, `dependencies.py`, JWT, Compose и зависимости делает Евгений. Utility делает Данил. Не создавай второй engine, `FastAPI()` или свой `SessionLocal`, не устанавливай новый фреймворк. Если нужен общий файл - сначала напиши Евгению.

## 1. Модуль Notification и тесты

**Начинай после пункта 1 задания Евгения.** Работай параллельно Данилу над Utility. Твой PR с Notification принимается первым из модулей, затем PR Данила; после них Евгений собирает общее приложение в своём пункте 3.

### Модель и валидация

- [ ] Перенести Notification в таблицу **`notification.notifications`** общей PostgreSQL-базы. Наследовать общий `Base`, пользоваться общей поддержкой UTC.
- [ ] Сохранить поля: `id`, `user_id` nullable, `recipient`, `channel`, `subject` nullable, `message`, `status`, `created_at`, `sent_at` nullable. UUID остаются совместимыми с исходником; ограничения каналов `EMAIL/SMS/PUSH`, статусов `PENDING/SENT/FAILED` сохраняются.
- [ ] Перенести ограничения входа: `user_id` - UUID либо null, `recipient` 1–255, `subject` до 255 либо null, `message` 1–5000 символов; строки очищаются по исходной Pydantic-схеме. Не разрешать произвольный channel.
- [ ] Ответ соответствует прежнему `NotificationResponse`: все перечисленные публичные поля, статус, UTC-даты с `Z`. Нельзя возвращать ORM-объект с ленивой загрузкой наружу.

### Публичный файл `api.py`

Другой модуль может импортировать только этот файл. Точная договорённость:

```python
class NotificationApi:
    def __init__(self, session_factory, *, fail_sending: bool = False): ...

    def send(
        self, *, user_id: str | None, channel: str,
        recipient: str, subject: str | None, message: str,
    ) -> NotificationResponse: ...
```

`NotificationResponse` доступен из этого же публичного файла; можно переэкспортировать Pydantic-модель из внутреннего `schemas.py`. Никакого публичного ORM. Реализуется только этот фасад, дополнительный абстрактный интерфейс не нужен.

- [ ] `send` валидирует аргументы по `NotificationCreate` **до** создания записи. Даже внутренний вызов не должен обходить ограничения данных.
- [ ] Открывает собственную сессию через переданный `session_factory`, а не получает сессию Utility и не хранит одну открытую сессию на все запросы.
- [ ] Создаёт запись `PENDING`, делает commit/refresh, пишет `notification_pending` с ID.
- [ ] Если `fail_sending=True`, **после этого commit**, но до `SENT`, выбрасывает `RuntimeError("Notification sending failed")`. Сохранённая запись остаётся `PENDING`, `sent_at=NULL`; исключение не подавляется фасадом.
- [ ] В нормальном режиме имитирует отправку, присваивает `SENT`, `sent_at` в UTC, делает второй commit/refresh и пишет `notification_sent`.
- [ ] Возвращает заполненный Pydantic `NotificationResponse`, безопасный после закрытия сессии. Сессия закрывается и при успехе, и при ошибке.
- [ ] Не импортирует Utility, не читает `utility.issues`, не создаёт JOIN/FK на чужие таблицы. Реальных EMAIL/SMS/PUSH-провайдеров не подключает.

### HTTP-адаптер `router.py`

`POST /notifications` сохраняется: его используют Transport и Billing, которые не объединяются в этой работе. Но Utility вызывает фасад напрямую, без сети.

- [ ] Создать `APIRouter`, маршрут `POST /notifications` со старой входной Pydantic-схемой, ответом `NotificationResponse`, кодом `201`.
- [ ] Сохранить обязательный `X-Service-Token` и безопасное сравнение из исходного `security.py`; при отсутствующем/неверном токене - `401`. Токен берётся из окружения общей конфигурации, не из тела запроса. При переносе helper можно оставить внутренний `security.py` в твоём модуле.
- [ ] Через `Depends(get_notification_api)` получить готовый фасад из `app.dependencies`, вызвать `send` и вернуть DTO. Не дублировать в router логику сохранения/отправки.
- [ ] Сбой фасада в прямом HTTP-вызове Notification даёт `500`; не превращать его в ложный `201`. За успешную заявку Utility при этом отвечает Данил своим перехватом ошибки.
- [ ] Не добавлять управляющий endpoint включения сбоя. Евгений передаёт `NOTIFICATION_FAIL_SEND` из окружения в конструктор, по умолчанию `False`.
- [ ] Для наполнения на чистой БД согласовать одну демонстрационную запись `SENT` с фиксированным UUID и тестовым получателем; seed идемпотентный, без удаления данных. Общий `init_db` вызывает его снаружи. Данил исключает seed из измеряемого прироста.

### Тесты `tests/test_notification.py`

Использовать отдельную тестовую PostgreSQL-БД и fixtures Евгения, не рабочие данные. SQL-проверки внутри тестов допустимы. Старый `conftest.py` со SQLite не копировать.

- [ ] Прямой вызов фасада сохраняет `SENT`, UUID и ненулевой `sent_at`; все поля ответа верны, даты UTC.
- [ ] `fail_sending=True` действительно выбрасывает `RuntimeError`; после открытия новой сессии запись находится в `PENDING`, `sent_at=NULL`.
- [ ] Неверные UUID/channel/пустые обязательные строки/слишком длинный message отклоняются, лишняя запись не создаётся.
- [ ] HTTP с правильным service-token даёт `201`, без него или с неправильным - `401`, неверное тело с правильным токеном - `422`.
- [ ] Логи содержат события с ID, но не service-token/Authorization/JWT. Несколько запросов не используют одну общую сессию.
- [ ] Показать Евгению результат команд `python -m pytest -q tests/test_notification.py` и замечания. Команду выполнять из `smart-city-monolith/` только с подготовленным безопасным тестовым окружением.

**Первый PR:** модуль, тесты и при готовности начальная часть отчёта. Не отмечать проверки выполненными, пока реально их не запускал. Если тест не проходит или инфраструктуры не хватает - отправить точный текст ошибки Евгению, не обходить проверку.

## Как создать ветку и отправить PR

Если копии нового репозитория ещё нет, выполнить один раз:

```bash
git clone https://github.com/dydojopka/SmartCityMonolith.git
cd SmartCityMonolith
```

Если она уже есть, открыть её каталог в терминале. Не путать с `SmartCity`. Создавать ветку после того, как Евгений сольёт каркас:

```bash
git status
git remote -v
git fetch origin
git switch main
git pull --ff-only origin main
git switch -c work/vaNYA
```

Если неизвестные изменения или ошибка Git - ничего не удалять, отправить Евгению текст ошибки. `git switch -c` используется один раз, потом `git switch work/vaNYA`. Не делать `reset --hard`, `push --force` или `git add -f .local`.

Перед коммитом запустить свои тесты в окружении Евгения. Затем из корня репозитория:

```bash
git diff
git add smart-city-monolith/app/modules/notification smart-city-monolith/tests/test_notification.py
git diff --cached
git commit -m "Добавить модуль уведомлений и публичный фасад"
git push -u origin work/vaNYA
```

Просмотр `git diff --cached` обязателен: там только твои проверенные файлы, без README и секретов. Это команды для первого PR; отчёт второго добавляется отдельно через `git add docs/report` после проверки содержимого. Коммиты выполняешь сам.

На GitHub открыть **Pull requests → New pull request**:

1. `base: main`, `compare: work/vaNYA`.
2. Заголовок, например «Модуль уведомлений и его тесты».
3. Описание: что сделано, какая команда тестов выполнена и результат, есть ли оставшиеся проблемы. Не вставлять сюда личные инструкции.
4. Вкладка **Files changed**: только согласованные файлы. Reviewer - Евгений. Если не готово - **Draft pull request**, не обычный готовый PR.
5. Исправления по ревью - обычный commit и `git push` в ту же ветку, PR обновится автоматически.

Перед продолжением работы после чужих PR и после слияния своего первого PR:

```bash
git fetch origin
git switch work/vaNYA
git merge origin/main
git push
```

Если появились конфликты, не выбирать «принять всё» - показать Евгению. Он поможет сохранить обе нужные правки. Команда использует **Create a merge commit**; до готовности отчёта ветку не удалять и историю не переписывать. Второй PR открывается из той же синхронизированной ветки.
